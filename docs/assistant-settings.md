# Assistant settings

The unstyled assistant settings component uses an injected ConfigurationService. Mode and Model are separate controls. Local runs Qwen; Online is saved but unavailable and disables Send. Auto is passed to the model framework, CPU maps to WASM, and WebGPU is an explicit request. Generation controls use a 256-token default, with sampling off. No hardware fallback is selected by the application.

Composition supplies browser storage and events to ConfigurationRepository. The repository owns the versioned preference record and reads current storage on relevant events; services and views never access storage keys. Missing preferences use defaults. Invalid or inaccessible storage produces a visible notice and valid session settings. Nothing clears unrelated storage or persists conversations.

Saved settings resolve before model channels are hosted. RuntimeConfigurationAdapter implements RuntimeConfigurationAdapterContract and adapts selected settings to RuntimeCoordinator commands. It translates shared status for ConfigurationService and starts the tab's channels after saved settings apply. RuntimeCoordinator publishes selected and active settings, drains accepted whole responses and coalesces queued edits before adopting the latest combination. Selection identities keep older snapshots from clearing a failed local choice. Tabs keep their own RagService and history. Generation-only changes retain model weights; backend/precision changes use the existing disposal and initialization protocol. No Web Locks, heartbeat, tab owner or parallel runtime is introduced.

Errors keep requested settings visible and Send unavailable. Retry resubmits the selection after restoring missing model connections. Switch back uses this client's last working selection; Restore defaults is available when none exists. Neither action silently clears history. Browsers may terminate workers or evict cached downloads; preferences are also subject to browser storage availability.

Verification uses public repository/service/adapter interfaces, native coordinator ports, actual component controls, production application journeys with labelled controlled drivers, and separate real CPU/cache checks. Follow [verification evidence storage](verification-evidence.md); run reports are artifacts, not committed files. Historical configuration work is reused selectively, excluding its superseded worker-ownership implementation.

ModelMetadataRepository reads the pinned model revision's file inventory and config through the injected JSON API. It caches validated metadata separately from preferences and model weights, keyed by metadata source, model source, ID and revision. Missing or denied cache access permits session-only discovery. Metadata requests have a ten-second deadline. Its errors and Retry model options action do not disable an already usable assistant. The component renders the service's model and precision choices; execution and generation controls remain application-supported choices. Auto precision is offered only when the framework's resolved variant is published. Discovery covers the configured decoder model's normal model*.onnx loading path, not arbitrary architectures or hardware compatibility.

The site configuration pins the model revision. RuntimeConfigurationAdapter passes it to generation; the generation pipeline and tokenizer load that same revision. RuntimeCoordinator reports the resource revision, and a tab does not report readiness against a different shared revision. Refreshing metadata never upgrades the revision, replaces preferences or downloads weights. A custom model mirror must supply its metadata endpoint. Introducing a pinned URL can require an initial download even when an older main URL was cached; subsequent sessions reuse the framework cache for the pinned files.
